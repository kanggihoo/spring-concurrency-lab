# Phase Evidence Portfolio Review

## 목적
프로젝트의 phase 산출물을 시니어 백엔드 엔지니어이자 포트폴리오 리뷰어 관점에서 검토한다.

중점적으로 확인할 사항:

- phase 계획서에서 요구한 작업이 실제로 완료되었는가.
- 최종 보고서가 계획서 및 evidence와 일관되는가.
- `report.md`만 읽어도 phase의 목적, 진행 방식, 주요 지표, 실험 조건, 데이터 개요, 사용자의 의도와 노력이 이해되는가.
- 지표에 신뢰 가능한 근거 자료와 명확한 측정 방법이 있는가.
- SQL `EXPLAIN ANALYZE`, k6 부하 테스트 지표, 애플리케이션 로그 등 evidence 원자료에 이상하거나 의심스러운 정황이 있는가.
- 작업 결과가 면접관이나 리뷰어에게 백엔드 역량을 잘 보여주는가.
- 누락된 작업, 약한 주장, 부족한 증거, 개선 기회가 명확히 드러나는가.

## 입력 자료
phase 이름만 제공되면 다음 표준 위치에서 자료를 자동으로 찾는다:

- phase 계획서: `docs/roadmap/<현재 phase>.md`
- phase 설명/사용법: `docs/phases/<현재 phase>/README.md`
- 최종 보고서: `docs/phases/<현재 phase>/report.md`
- 실제 측정 evidence: `docs/evidence/<현재 phase>/`

자료가 없거나 경로가 다르면 사용자에게 요청한다. 선택 context로 프로젝트 목표, 예상 독자, 사용자가 보여주고 싶은 백엔드 강점이 있으면 함께 반영한다. 경로가 제공되면 반드시 파일을 읽고 검토한다. 파일명만 보고 판단하지 않는다.

## 검토 절차

1. phase 계획서와 `README.md`를 읽고 필수 산출물, 성공 기준, 기대 지표, 실행/동작 방식, 학습 목표를 추출한다.
2. `report.md`를 독립 문서로 읽고 phase의 목적, 접근 방식, 실험 흐름, 주요 결과, 사용 데이터, 측정 방법, 사용자의 의도와 노력이 이해되는지 평가한다.
3. 보고서의 각 주장과 결과가 계획서, README, evidence의 어떤 항목에 대응되는지 매핑한다.
4. evidence 파일을 살펴보고 각 파일이 무엇을 증명하는지, 측정이 어떻게 수행되었는지, 재현 가능한지 확인한다.
5. k6, SQL `EXPLAIN ANALYZE`, benchmark 로그, 애플리케이션 로그, DB 지표 등 원자료를 보고 보고서의 숫자와 설명이 일치하는지 검증한다.
6. 계획서, README, 보고서, evidence 사이의 불일치, 누락 작업, 근거 없는 주장, 불명확한 방법론, 의심스러운 측정 결과를 비교한다.
7. 백엔드 채용/면접 관점에서 포트폴리오 전달력을 평가하고, 개선 사항을 구체적 우선순위로 제안한다.

## 필수 점검

- Claim -> Evidence 매트릭스: `report.md`의 주요 주장마다 뒷받침하는 evidence 파일, 지표, 로그, 스크립트, 실행 조건을 연결한다.
- `report.md` 독립성 테스트: README나 evidence를 보기 전에도 무엇을 해결하려 했는지, 어떤 가설을 세웠는지, 어떤 실험을 했는지, 어떤 데이터/부하 조건을 썼는지, 결과를 왜 그렇게 해석했는지, 한계와 다음 단계가 무엇인지 답할 수 있어야 한다.
- 포트폴리오 서사: 문제 인식 -> 가설 -> 실험 설계 -> 측정 -> 분석 -> 의사결정 -> 한계 인식 -> 다음 개선 흐름이 보이는지 확인한다.
- 면접 방어 가능성: 보고서를 본 면접관이 물어볼 질문을 예상하고, 현재 문서와 evidence만으로 답변 가능한지 평가한다.
- 행동 가능한 개선안: "보강 필요" 같은 추상 표현 대신 보고서에 추가할 문단, evidence에 추가할 파일, 다시 측정할 항목, 다이어그램, README 실행 절차처럼 바로 실행 가능한 형태로 제안한다.
- Docusaurus 전환 가능성: `report.md`가 충분하면 내용을 반복하지 말고 `Full technical report: ./report.md`처럼 참조 링크를 남기고, 공개용 `portfolio.mdx` 생성 가능 여부를 판단한다. 상세 작성 지침이 필요하면 [PORTFOLIO_MDX.md](PORTFOLIO_MDX.md)를 읽는다. 사용자가 `profile.mdx`라고 말하면 공개용 포트폴리오 MDX 문서인 `portfolio.mdx` 의도로 해석한다.

## 검토 기준
사용자가 다른 기준을 요청하지 않았다면 다음 기준을 사용한다:

- 완료도: 계획된 작업, 실험, 문서, 후속 조치가 모두 다뤄졌는가.
- 보고서 단독 완결성: `report.md`만으로 무엇을 왜 했고, 어떤 방식으로 진행했고, 어떤 지표로 판단했는지 이해되는가.
- 증거 품질: raw data, 로그, 스크립트, 스크린샷, benchmark 결과, 설정, 재현 절차가 주장을 뒷받침하는가.
- 지표 타당성: 무엇을 측정했는지, 측정 환경, workload, sample size, 단위, 전후 비교, 한계가 명확한가.
- 부하 테스트 설명력: k6를 사용했다면 VU 수, duration, ramp-up/ramp-down, scenario, endpoint, request mix, thresholds, 주요 metric(`http_req_duration`, `http_req_failed`, `http_reqs`, `iterations`, p95/p99 등)이 설명되는가.
- 데이터 개요: 테스트에 사용된 데이터 규모, 생성 방식, 주요 분포, 초기 상태, 격리 방식, 재사용 여부가 설명되는가.
- SQL 분석 신뢰성: `EXPLAIN ANALYZE`를 사용했다면 실행 계획, 실제 실행 시간, rows, loops, index 사용 여부, seq scan 여부, buffer hit/read, 병목 후보가 보고서 주장과 맞는가.
- 이상 징후 탐지: evidence의 지표가 보고서 결론과 맞지 않거나, 샘플 수가 부족하거나, 오차가 크거나, warm-up/캐시/락 경합/커넥션 풀/DB 상태 때문에 왜곡됐을 가능성이 있는가.
- k6 의심 패턴: 평균은 좋아졌지만 p95/p99가 나빠졌는가, 실패율이 있는데 성공 응답만 해석했는가, VU/duration이 너무 낮은가, warm-up 없이 첫 실행만 사용했는가, threshold 실패를 무시했는가.
- SQL 의심 패턴: `EXPLAIN ANALYZE`의 estimated rows와 actual rows 차이가 큰가, index scan 여부만 보고 execution time/buffer/loops를 무시했는가, 캐시 hit 이후 결과를 DB 성능 개선으로 과대 해석했는가.
- 기술적 깊이: 단순히 결과만 말하지 않고 백엔드가 왜 그렇게 동작했는지 설명하는가.
- 의사결정 품질: tradeoff, 기각한 대안, 제약, 운영 리스크가 드러나는가.
- 포트폴리오 가독성: 면접관이 문제, 접근, 증거, 결과, 학습을 빠르게 이해할 수 있는가.
- 사용자 의도와 노력: 사용자의 설계 선택, 시행착오, 분석 과정, 추가 실험, 한계 인식이 generic summary 뒤에 숨지 않고 드러나는가.

## 출력 형식
사용자가 다른 언어를 요청하지 않는 한 한국어로 응답한다.

이 스킬 자체를 작성하거나 수정하는 동안에는 사용자가 최종 승인하기 전까지 `SKILL.md` 초안도 한국어로 작성한다. 사용자가 만족하여 최종화를 요청하면 최종 `SKILL.md`를 영어로 재작성한다.

다음 구조를 사용한다:

```md
**총평**
[현재 상태와 포트폴리오 전달력에 대한 1-3문장 요약]

**완료 여부**
- [완료/부분 완료/누락] [phase 요구사항]: [근거와 판단 이유]

**증거 자료 검토**
- [강함/약함/누락] [주장 또는 지표]: [어떤 증거가 뒷받침하는지, 무엇이 부족한지]

**Claim -> Evidence 매트릭스**
- [주장]: [근거 파일/지표] -> [충분/부분/부족] [판단]

**지표 및 이상 징후**
- [정상/의심/불충분] [k6, SQL EXPLAIN ANALYZE, 로그, DB 지표 등]: [evidence 기반 판단과 확인할 점]

**백엔드 포트폴리오 관점**
- 장점: [드러나는 백엔드 역량]
- 개선: [의도, 사고 과정, 기술 깊이를 더 명확히 하기 위한 개선점]

**면접관 예상 질문**
- [질문]: [현재 문서만으로 답변 가능 여부와 보강 포인트]

**Docusaurus portfolio.mdx 제안**
- 상태: [바로 작성 가능/작성 전 보강 필요]
- 참조: [충분한 report.md 링크 또는 보강할 report.md 섹션]
- 구조: [portfolio.mdx에 들어갈 섹션]
- 시각화: [표/그래프/이미지/React chart component로 표현할 지표]

**우선순위 개선사항**
- P0: [공유 전 반드시 수정할 항목]
- P1: [중요한 개선 항목]
- P2: [완성도를 높이는 polish 항목]

**추가하면 좋은 자료**
- [구체적인 artifact, 지표, 다이어그램, 스크립트, 설명]
```

## 규칙

- 직접적이고 evidence 기반으로 판단한다. 근거 없는 결과를 칭찬하지 않는다.
- "없음"과 "있지만 불명확함"을 구분한다.
- 가능하면 파일 경로와 line number를 인용한다.
- 최종 숫자가 그럴듯해 보여도 측정 방법론이 빠져 있으면 실제 gap으로 본다.
- 추상적 조언보다 구체적인 rewrite, checklist, artifact 제안을 우선한다.
- evidence가 부족하면 어떤 자료가 있어야 해당 주장이 방어 가능한지 명확히 말한다.
- 사용자가 명시적으로 요청하지 않는 한 프로젝트 파일을 수정하지 않는다.
