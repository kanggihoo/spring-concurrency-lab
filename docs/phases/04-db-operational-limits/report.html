핵심 결론

Phase 4의 차이는 정합성이 아니라 운영 성능이다. 모든 조건에서 좌석 수 정합성은 깨지지 않았고, 실제 판단 기준은 처리량, p95/p99, pool pressure, DB row lock wait였다.

기본 전략

Atomic Conditional Update

Phase 5 Redis 비교의 DB 기준은 Atomic으로 둔다. 정합성을 유지하면서 pool 확장에 따른 처리량 개선이 가장 명확했다.

운영 기준

Pool 10 / Pool 50 분리

Pool 10은 보수적 운영 기준, Pool 50은 이번 로컬 실험에서 확인한 DB throughput ceiling으로 사용한다.

주의 전략

Pessimistic Lock

정합성 reference로는 유지하지만, 단일 row 고경합에서는 pool을 키울수록 DB lock wait가 쌓일 수 있다.

Atomic Pool Result

Atomic은 pool 2에서 pool 5로 올릴 때 가장 큰 개선이 있었다. pool 10 이후에는 개선 폭이 작아지고, pool 50은 이번 로컬 측정의 최고 처리량 지점이다.

운영 해석: pool 10은 connection 사용량을 과도하게 늘리지 않으면서 주요 개선을 대부분 확보한 보수적 균형점이다. pool 50은 Redis와 비교할 DB 상한선으로 기록한다.

Pessimistic Pool Result

Pessimistic Lock은 connection pool을 늘려도 처리량이 안정적으로 증가하지 않았다. pool 50에서는 Hikari Pending은 줄었지만 DB row lock wait가 크게 늘었다.

병목 위치: pool 부족이 아니라 같은 Concert row를 잡기 위한 DB 내부 대기다. pool 10 snapshot은 waiting lock row 8개, pool 50 snapshot은 48개를 기록했다.

Pessimistic Timeout Result

PostgreSQL lock_timeout을 200ms, 500ms, 1000ms로 바꿨지만 현재 부하에서는 timeout 응답이 관측되지 않았다.

해석 제한: 이번 evidence만으로 lock_timeout이 controlled failure를 만든다고 결론낼 수 없다. lock hold time을 의도적으로 늘린 별도 검증이 필요하다.

Phase 5 입력

Redis 비교 기준

Atomic Conditional Update pool 10을 보수적 DB 운영 기준으로 사용한다. 같은 k6 shape에서 Redis 전략이 이 기준을 넘어서는지 비교한다.

DB 상한 비교

Atomic Conditional Update pool 50은 이번 Phase 4에서 관측한 DB throughput ceiling이다. Redis가 DB 상한선과 비교해 어떤 비용과 이득을 갖는지 확인한다.

정합성 불변식

전략이 바뀌어도 Reservation 100건, Remaining Seats 0, Seat Count Inconsistency 0, Overbooking false를 동일하게 만족해야 한다.

추가 검증 대상

lock_timeout은 guardrail 후보로 남긴다. 운영 정책 확정 전에는 transaction 지연 또는 long lock hold를 만드는 별도 실험이 필요하다.
